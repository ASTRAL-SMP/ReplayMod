# ReplayMod: GPUオフロード方針メモ（2026-05-11）

## 結論

- **「RAM依存 → GPU依存」へ全面移行は不可**です。ReplayModの処理には、
  - リプレイデータ読み込み/解凍
  - パケット再生順序の維持
  - エンティティ/チャンク状態更新
  など、**GPUで直接実行できないロジック**が多く含まれます。
- ただし、**レンダリングと動画エンコードはGPU化の効果が大きい領域**です。

## 何がGPU化できるか

### 1) 動画エンコード（GPU）
- 既存コードにはFFmpegハードウェアエンコーダ選択ロジックがあり、
  `h264_nvenc` / `h264_vaapi` / `h264_videotoolbox` などを利用可能。
- さらにHEVC/AV1系の拡張も進んでおり、CPU負荷を下げつつ書き出し時間短縮が見込める。

### 2) メッシュ生成の並列化（CPU）+ アップロード（GPU）
- OpenGL制約上、`glBufferData` 等のアップロードはレンダースレッドで行う必要があるため、
  **完全GPU化ではなくハイブリッド化**が現実的。
- 実装方針は「頂点データ生成を並列化し、GPUアップロードをフレーム予算内で処理」。

## 何がGPU化しにくいか

- リプレイストリームのシーク/デコード/順序保証（ViaVersion状態含む）
- Minecraftクライアント内部のワールド更新・エンティティ同期
- Javaヒープ上の管理構造（時系列インデックスや追跡テーブル）

> これらはGPUへ移すより、データ構造最適化・並列化・I/Oパイプライン最適化の効果が高いです。

## 依存関係追加の提案

### 目的別

1. **CPU側メモリ圧縮・スナップショット効率化**
   - `org.lz4:lz4-java:1.8.0`
   - GPU依存そのものではないが、シーク最適化の土台として有効。

2. **GPUエンコード能力の利用**
   - Java依存というより **FFmpeg実行環境依存**（ドライバ/ランタイム）
   - Linux: VAAPI (`/dev/dri/renderD128`)
   - NVIDIA: NVENC（対応ドライバ+ハードウェア）

3. **（将来）計算系GPU化**
   - OpenCL/CUDA等のJNI依存を追加する案はあるが、
     クロスプラットフォーム運用コストと保守負担が非常に高く、現時点では非推奨。

## 推奨アクション

1. **現行方針維持（推奨）**
   - CPU: シーク/インデックス/状態更新を最適化
   - GPU: 描画・エンコードのみ強化

2. **ベンチマーク前提で段階導入**
   - Export時間（1分クリップ）
   - 再生時frame time（99p）
   - ヒープ使用量（10分再生後GC）

3. **「全面GPU化」は目標から外す**
   - 代わりに「ユーザー体感に効くホットパスのGPU/並列化」を優先。
